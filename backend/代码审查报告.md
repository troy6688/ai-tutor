## 一、安全问题（Security）

### 1. CORS 配置过于宽松

| 项目 | 内容 |
|------|------|
| **文件** | `main.py` |
| **行号** | 第 24-29 行 |
| **严重程度** | 高 |
| **问题描述** | `allow_origins=["*"]` 允许任意来源跨域访问，存在 CSRF 风险，攻击者可诱导用户在恶意网站调用后端接口。 |
| **改进建议** | 生产环境应限制为具体域名列表，如 `allow_origins=["https://yourdomain.com"]`；本地开发可单独配置。建议通过环境变量管理允许列表。 |

### 2. 会话永不过期，无过期清理机制

| 项目 | 内容 |
|------|------|
| **文件** | `db.py` |
| **行号** | 第 32-36 行（表定义）、第 88-97 行（创建会话） |
| **严重程度** | 高 |
| **问题描述** | `sessions` 表只有 `created_at` 没有 `expires_at`，token 一旦签发永久有效。token 泄露后攻击者可永久冒用身份；数据库中无效会话也会持续累积。 |
| **改进建议** | ① 表中增加 `expires_at` 字段，创建会话时设置过期时间（如 7 天）；② `get_user_by_token` 查询时校验是否过期；③ 定期清理过期会话或在登录时自动清理。 |

### 3. 登录接口无暴力破解防护

| 项目 | 内容 |
|------|------|

| **严重程度** | 高 |

### 4. Chat / TTS 接口缺少认证，可被匿名滥用

### 6. 用户名缺少格式校验，存在注入风险（非 SQL）

| 项目 | 内容 |
|------|------|

### 7. Stats 中"最近练习"按分数排序而非时间排序

| 项目 | 内容 |
|------|------|
| **文件** | `routers/stats.py` |
| **行号** | 第 48 行 |
| **严重程度** | 高 |

| **改进建议** | ① `db.get_user_progress` 需要返回 `updated_at` 字段；② 按 `updated_at` 降序排序。 |

### 8. db.get_user_progress 未返回 updated_at 字段

| 项目 | 内容 |

### 9. 多选题判分逻辑可能存在歧义

| 项目 | 内容 |
|------|------|
| **文件** | `routers/quiz.py` |
| **行号** | 第 28-29 行 |
| **严重程度** | 中 |
| **问题描述** | 多选题判分使用 `set(_trim(user).upper()) == set(_trim(q["answer"]).upper())`，即把字符串当字符集合比较。这隐含假设答案格式是"选项字母直接拼接"（如 `"ABC"`）。如果前端传的是逗号分隔的列表或数组，判分会完全错误。且代码未做格式校验和断言。 |
| **改进建议** | ① 明确约定多选题答案格式（建议统一为列表/数组）；② 增加格式校验，不符合预期时返回明确错误；③ 若使用字符串格式，应在文档和代码注释中明确说明。 |

### 10. Progress 保存时 correct/total 无合法性校验

| 项目 | 内容 |
|------|------|
| **文件** | `routers/progress.py`、`db.py` |

| **改进建议** | ① Pydantic 模型中增加 `Field(ge=0)` 约束；② 业务层校验 `correct <= total`；③ 校验 `point_id` 在知识库中存在。 |

### 11. TTS POST 接口参数通过 Query 传递，不符合规范且有长度限制

### 12. TTS 接口缺少异常处理

## 三、数据一致性与并发（Data Consistency）

### 13. SQLite 写操作未加锁，并发写入可能抛 "database is locked"

| 项目 | 内容 |
|------|------|
| **文件** | `db.py` |
| **行号** | 第 64-78 行（create_user）、第 88-97 行（create_session）、第 100-106 行（clear_session）、第 130-141 行（upsert_progress） |
| **严重程度** | 高 |
| **问题描述** | `_lock` 仅在 `init_db` 中使用，其他所有写操作都没有加锁。SQLite 在多线程并发写入时容易出现 `sqlite3.OperationalError: database is locked` 错误。随着用户量增加，该问题会频繁出现。 |
| **改进建议** | ① 所有写操作统一使用 `_lock` 保护；或 ② 启用 WAL 模式（`PRAGMA journal_mode=WAL`）提升并发能力；或 ③ 使用连接池 + 重试机制。 |

### 14. 数据库无外键约束，可能产生孤儿数据

| 项目 | 内容 |
|------|------|
| **文件** | `db.py` |
| **行号** | 第 32-36 行（sessions）、第 37-46 行（progress） |
| **严重程度** | 中 |
| **问题描述** | `sessions.user_id` 和 `progress.user_id` 都没有外键约束。如果用户被删除，关联的会话和进度记录会变成孤儿数据残留。同时 SQLite 默认未开启外键支持。 |
| **改进建议** | ① 连接建立后执行 `PRAGMA foreign_keys = ON`；② 表定义中增加 `FOREIGN KEY (user_id) REFERENCES users(id)` 约束；③ 考虑级联删除策略。 |

### 15. 时间字段使用本地时间（datetime.now）

| 项目 | 内容 |
|------|------|
| **文件** | `db.py` |
| **行号** | 第 70 行、第 93 行、第 137 行 |
| **严重程度** | 低 |
| **问题描述** | 所有时间戳使用 `datetime.now().isoformat()` 记录本地时间。如果服务器时区变更或部署在不同时区的机器上，时间会出现混乱，也不利于跨时区展示。 |
| **改进建议** | 使用 `datetime.utcnow()` 或 `datetime.now(timezone.utc)` 存储 UTC 时间，前端根据用户时区转换展示。 |

## 四、性能问题（Performance）

### 16. store.get_point 线性查找，O(n) 时间复杂度

| 项目 | 内容 |
|------|------|
| **文件** | `store.py` |
| **行号** | 第 36-41 行 |
| **严重程度** | 中 |
| **问题描述** | `get_point(point_id)` 每次调用都遍历所有知识点进行线性搜索。虽然当前数据量不大，但随着知识点增多（如几百个），频繁调用时会有性能损耗。`get_points()` 也是每次全量过滤。 |
| **改进建议** | 在 `load_kb` 时构建 `{id: point}` 的字典索引和按 grade 分组的索引，查询时直接 O(1) 或 O(1)+O(k) 访问。 |

### 17. catalog 接口每次都重建目录树，无缓存

| 项目 | 内容 |
|------|------|
| **文件** | `routers/catalog.py` |
| **行号** | 第 26-50 行 |
| **严重程度** | 低 |
| **问题描述** | `get_catalog` 每次请求都遍历所有知识点、用 `next()` 线性查找来构建章节目录树。知识点数据是静态的（来自 kb.json），重复计算属于浪费。 |
| **改进建议** | 在 `store.py` 中预构建并缓存目录树结构，按 grade 分别缓存；数据 reload 时同步更新缓存。 |

### 18. 每次数据库操作都新建连接，无连接复用

| 项目 | 内容 |
|------|------|
| **文件** | `db.py` |
| **行号** | 第 14-17 行 |
| **严重程度** | 低 |
| **问题描述** | 每个数据库函数都调用 `get_conn()` 新建连接、用完即关。SQLite 连接创建开销不大，但频繁打开关闭文件仍有一定损耗。 |
| **改进建议** | 可考虑使用线程本地存储（threading.local）维护每线程一个连接，或使用轻量连接池。优先级不高。 |

### 19. TTS 相同文本重复合成，无缓存

| 项目 | 内容 |
|------|------|
| **文件** | `routers/tts.py` |
| **行号** | 第 21-31 行 |
| **严重程度** | 低 |
| **问题描述** | 相同的文本 + 音色 + 语速每次都会重新调用 edge-tts 合成，浪费时间和网络资源。对于知识点讲解这类固定内容，重复合成率很高。 |
| **改进建议** | 增加本地缓存（如以文本哈希 + 音色为 key 的文件缓存），命中则直接返回缓存音频。 |

## 五、代码质量与架构（Code Quality & Architecture）

### 20. 错误返回格式不统一（HTTPException vs 自定义 code）

| 项目 | 内容 |
|------|------|
| **文件** | 全局 |
| **行号** | `auth.py` 第 26 行；`catalog.py` 第 58 行；`quiz.py` 第 42、60 行 等 |
| **严重程度** | 中 |
| **问题描述** | 项目中混用两种错误返回方式：① 部分接口使用 `raise HTTPException()` 返回 FastAPI 标准格式（`{"detail": "..."}`）；② 另一部分返回自定义格式 `{"code": 1, "message": "...", "data": null}`。前端需要处理两种错误格式，容易遗漏。 |
| **改进建议** | 统一使用自定义格式。建议添加全局异常处理器，将 `HTTPException` 和未捕获异常都转换为统一的 `{code, message, data}` 格式。 |

## 七、错误处理（Error Handling）

### 27. chat.py 异常捕获过于宽泛，且暴露内部错误信息

| 项目 | 内容 |
|------|------|
| **文件** | `routers/chat.py` |
| **行号** | 第 49-50 行 |
| **严重程度** | 中 |
| **问题描述** | `except Exception as e` 捕获所有异常，且直接将异常信息 `e` 返回给前端。这可能泄露 API 密钥、内部 URL 等敏感信息（如 requests 异常可能包含请求详情）。 |
| **改进建议** | ① 区分不同异常类型（网络超时、HTTP 错误、解析错误等）；② 返回给用户的错误信息脱敏，只保留友好提示；③ 详细错误记录到服务端日志。 |

### 28. 全局缺少统一异常处理和日志记录

| 项目 | 内容 |
|------|------|
| **文件** | `main.py` |
| **行号** | - |
| **严重程度** | 中 |
| **问题描述** | 没有全局异常处理器（`@app.exception_handler`），未捕获的异常会以 FastAPI 默认格式返回。同时整个项目没有日志记录系统，出现问题难以排查。 |
| **改进建议** | ① 添加全局异常处理器，统一返回 `{code, message, data}` 格式；② 接入 Python logging 模块，记录请求、错误、慢查询等关键信息。 |
